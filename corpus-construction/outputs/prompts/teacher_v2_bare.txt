=============================== PROMPT BODY ===============================
You are coding ONE app-store review of a mobile game against the codebook below.

A review usually describes more than one mechanic. Assign every label the review
supports, not the single best one (R9). Read the review closely first, including what

GLOBAL RULES

R1. One review is one unit. Assign each applicable meso label at most once per review, regardless of how many times the pattern appears in the text.
R2. Assign a label only when the review describes a game mechanic or design behaviour. Never assign from rating, tone, or general dissatisfaction alone.
R3. Record the exact quoted span that triggered each label. A label with no recorded span is invalid and must be removed.
R4. Assign the label the recorded span satisfies. Never assign because the game is known to contain the pattern, or because the pattern usually co-occurs with one already assigned.
R5. Every entry in a label's indicators list is an instance of that pattern, whether tagged [low-level], [dp-combo], or [indicators]. A span that names an instance assigns its meso label; a meso label assigns its high-level class. Alternate definitions (Alt. def.) are restatements of the meso definition, not instances.
R6. When no meso label satisfies R2 and R3, assign NONE. NONE is a blank cell.
R7. Assign labels irrespective of the reviewer's approval or disapproval.
R8. Code the mechanic described, not the reviewer's evaluation of it. "Generous battle pass" and "predatory battle pass" both describe a battle pass.
R9. When two labels both fit and no boundary rule separates them, assign both.
R10. If a game mechanic is not clear from the review's context, an external search can be used. Justify the search and tag the search query along with the review.
R11. Assign NONE when the text attributes a specific behavior to a bug, glitch, error, or technical fault, as dark patterns are deliberate design choices rather than technical malfunctions. A general mention that a game is buggy does not suppress labels on unrelated, functional design behaviors. However, assign the relevant dark pattern label if the underlying game rule itself imposes a penalty, even if a malfunction triggered it. For instance, if a crash causes a player to lose daily rewards or forfeit match progress, assign the appropriate label because missing a login or quitting a session carries that explicit design penalty regardless of why it happened.
R12. Code only the mechanics that the text explicitly describes as currently present in the game. Requests, suggestions, or hypothetical additions, such as wishing for a feature or asking to watch ads for coins, do not trigger tags for the proposed mechanics. However, this restriction applies exclusively to the non-existent feature itself. If the text mentions an existing game behavior or pattern alongside a suggestion, that active mechanic remains fully codable under any label it matches.
R13. Code only design encountered within the game application. Advertising the developer places in third-party apps, store-listing content, and marketing material are outside the unit even where the behaviour would satisfy a label: including deceptive dismissal controls, emotional appeals to install or return, and misrepresented gameplay. Push notifications sent by the installed game are within scope, being part of the installed product. Where a review describes both out-of-game marketing and in-game design, code the in-game spans only. Exception: Look at Friend Spam and Impersonation's "Destination of the message" rule.
